# sport-trend.ru — разделы каталога открывают один и тот же шаблон товара

## Симптом

При клике на любой раздел каталога (например «Лёгкая атлетика») вместо списка
товаров раздела открывается одна и та же детальная страница товара
(шаблон `element`). Ожидаемое поведение: URL раздела отдаёт список товаров
этого раздела.

## Что это означает технически

В 1С-Битрикс каталог почти всегда собран на **комплексном компоненте**
`bitrix:catalog` с включённым ЧПУ (`SEF_MODE = Y`). Комплексный компонент сам
разбирает часть URL после своей папки (`SEF_FOLDER`, обычно `/catalog/`) и
решает, какую страницу подключить:

| Страница компонента | Файл внутри компонента | Что показывает |
|---|---|---|
| `sections` | `sections.php` | список подразделов |
| `section`  | `section.php`  | **список товаров раздела** |
| `element`  | `element.php`  | карточка товара |

Симптом «везде карточка товара» значит ровно одно: **маршрутизатор отдаёт
страницу `element` на URL, который должен резолвиться в `section`**. Причин у
этого ограниченное число — ниже они в порядке убывания вероятности.

---

## Причина №1 — битые правила в `/bitrix/urlrewrite.php` (самая частая после переезда/восстановления)

`urlrewrite.php` — это таблица маршрутов Битрикса. Каждое правило: регулярка
`CONDITION` → физический файл `PATH`. При переносе сайта на другой хостинг или
при восстановлении из резервной копии этот файл регулярно приезжает битым,
пустым или с чужими правилами.

Опасный вид правила — слишком широкое условие, ведущее на `element.php`:

```php
array(
    "CONDITION" => "#^/catalog/#",          // ловит ВСЕ url каталога
    "RULE"      => "",
    "ID"        => "bitrix:catalog.element",
    "PATH"      => "/catalog/element.php",  // и всегда отдаёт карточку товара
),
```

Правильное правило для комплексного компонента должно вести на `index.php`
папки каталога:

```php
array(
    "CONDITION" => "#^/catalog/#",
    "RULE"      => "",
    "ID"        => "bitrix:catalog",
    "PATH"      => "/catalog/index.php",
),
```

### Проверка

```bash
cat /bitrix/urlrewrite.php
```

Смотрим: есть ли правило с `PATH => "/catalog/index.php"`; нет ли раньше него
правила с более широким `CONDITION`, ведущего на другой файл. **Порядок важен:
срабатывает первое подошедшее правило сверху вниз.**

### Исправление

Не правьте файл руками, если не уверены — Битрикс умеет пересобрать его сам:

> **Админка → Настройки → Настройки продукта → Обработка адресов (urlrewrite)**
> → кнопка **«Переиндексировать»** (`/bitrix/admin/urlrewrite_index.php`)

Переиндексация сканирует `.php`-файлы сайта, находит комплексные компоненты и
заново строит корректные правила. Перед этим сделайте копию:

```bash
cp /bitrix/urlrewrite.php /bitrix/urlrewrite.php.bak-$(date +%F)
```

Права на файл должны быть на запись (`644`, владелец — пользователь php-fpm),
иначе переиндексация молча ничего не сохранит.

## Причина №2 — сломаны SEF-шаблоны URL в настройках компонента

Файл: `/catalog/index.php` (или тот, что указан в `PATH` правила). Внутри —
вызов `$APPLICATION->IncludeComponent("bitrix:catalog", ...)` с массивом
`SEF_URL_TEMPLATES`.

### Как должно быть (значения по умолчанию)

```php
"SEF_MODE"   => "Y",
"SEF_FOLDER" => "/catalog/",
"SEF_URL_TEMPLATES" => array(
    "sections"     => "",
    "section"      => "#SECTION_CODE_PATH#/",
    "element"      => "#SECTION_CODE_PATH#/#ELEMENT_CODE#/",
    "compare"      => "compare.php?action=#ACTION_CODE#",
    "smart_filter" => "#SECTION_CODE_PATH#/filter/#SMART_FILTER_PATH#/apply/",
),
```

Ключевое: у `element` **на один сегмент пути больше**, чем у `section`. Именно
это позволяет роутеру их различать.

### Типовые поломки

1. **`element` стал таким же «коротким», как `section`:**

   ```php
   "section" => "#SECTION_CODE#/",
   "element" => "#ELEMENT_CODE#/",   // ← неоднозначно, шаблоны конфликтуют
   ```

   Оба шаблона матчат `/catalog/legkaya-atletika/`. Разбор идёт по порядку
   элементов массива, и `element` может выигрывать — получаем карточку товара
   на каждом разделе. Ровно наш симптом.

2. **`section` пустой или удалён из массива** — раздел резолвить нечем,
   выигрывает `element`.

3. **`element` содержит `#SECTION_CODE_PATH#` без `#ELEMENT_CODE#`** —
   шаблон вырождается в шаблон раздела.

### Исправление

Вернуть шаблоны к значениям выше — либо прямо в коде `/catalog/index.php`,
либо через визредактор: открыть страницу в режиме правки → настройки
компонента «Каталог» → блок **«Управление адресами страниц»**. После правки
обязательно **переиндексировать urlrewrite** (см. Причина №1) — правила
маршрутизации кэшируются в `urlrewrite.php`.

## Причина №3 — у разделов пустой символьный код (`CODE`)

`#SECTION_CODE_PATH#` строится из поля **Символьный код** раздела инфоблока.
После обмена с 1С или переимпорта каталога коды часто затираются. Тогда все
ссылки на разделы вырождаются в одинаковый URL, и что откроется — лотерея.

### Проверка

**Админка → Контент → Каталог (инфоблок) → Разделы** — колонка «Символьный
код». Если пусто у «Лёгкая атлетика» и остальных — это причина.

Через SQL (только чтение, `IBLOCK_ID` подставьте свой):

```sql
SELECT ID, NAME, CODE, IBLOCK_SECTION_ID, ACTIVE
FROM b_iblock_section
WHERE IBLOCK_ID = <ID_каталога>
ORDER BY LEFT_MARGIN;
```

### Исправление

Массово сгенерировать коды: **Настройки инфоблока → вкладка «SEF» /
«Транслитерация»** — включить «Транслитерировать символьный код из названия»
для разделов, затем пересохранить разделы (или прогнать скриптом
`CIBlockSection::Update` с `CODE => CUtil::translit($name,'ru')`).

Важно: смена кодов меняет URL разделов. Если старые URL были в индексе
поисковиков — заранее подготовьте 301-редиректы.

## Причина №4 — кэш отдаёт одну и ту же страницу на все URL

Два независимых слоя:

* **Кэш компонента** (`/bitrix/cache/`) — если в кастомном шаблоне
  `component_epilog` или в `.parameters.php` потеряна переменная раздела,
  ключ кэша получается одинаковым для всех разделов, и первый закэшированный
  раздел показывается на всех.
* **Композитный кэш** (`/bitrix/html_pages/`) — статические HTML-снимки. При
  битом роутинге туда попадает снимок карточки товара и раздаётся дальше
  уже независимо от исправленного PHP.

### Проверка

Добавьте к URL раздела произвольный параметр — он ломает попадание в кэш:

```
https://sport-trend.ru/catalog/legkaya-atletika/?nocache=1
```

Если с параметром раздел открывается **правильно**, а без него — карточка
товара, проблема в кэше.

### Исправление

**Админка → Настройки → Настройки продукта → Автокэширование → «Очистить
файлы кэша»** (все типы, включая композит). Либо:

```bash
rm -rf /bitrix/cache/* /bitrix/managed_cache/* /bitrix/html_pages/*
```

Если после сброса симптом возвращается — кэш не причина, а следствие; чините
Причину №1/№2, потом снова сбрасывайте кэш.

## Причина №5 — перехват на уровне веб-сервера или `init.php`

Проверить в порядке убывания вероятности:

1. `.htaccess` в корне и в `/catalog/` — нет ли `RewriteRule`, уводящего всё
   на один файл. Штатный блок Битрикса выглядит так:

   ```apache
   RewriteCond %{REQUEST_FILENAME} !-f
   RewriteCond %{REQUEST_FILENAME} !-l
   RewriteCond %{REQUEST_FILENAME} !-d
   RewriteCond %{REQUEST_FILENAME} !/bitrix/urlrewrite.php$
   RewriteRule ^(.*)$ /bitrix/urlrewrite.php [L]
   ```

2. `/bitrix/php_interface/init.php` — обработчики `OnPageStart` /
   `OnBeforeProlog`, делающие безусловный `include`/`LocalRedirect`.

3. Физические папки-«призраки»: если по пути `/catalog/legkaya-atletika/`
   лежит реальная папка с `index.php`, веб-сервер отдаст её, а не роутер
   Битрикса — правило `!-d` из блока выше пропустит запрос мимо urlrewrite.

   ```bash
   ls -la /catalog/
   ```

## Порядок действий (рекомендуемый)

1. Сделать полную резервную копию (**Настройки → Инструменты → Резервное
   копирование**) — все дальнейшие шаги обратимы только при наличии копии.
2. Проверить кэш (Причина №4, тест с `?nocache=1`) — 30 секунд, сразу отсекает
   целый класс версий.
3. Открыть `/bitrix/urlrewrite.php`, найти правила для `/catalog/`
   (Причина №1). Сохранить копию, переиндексировать.
4. Открыть `/catalog/index.php`, сверить `SEF_URL_TEMPLATES` с эталоном
   (Причина №2). Поправить, снова переиндексировать.
5. Проверить символьные коды разделов (Причина №3).
6. Сбросить весь кэш, проверить раздел «Лёгкая атлетика» в приватном окне.

После каждого шага проверять URL раздела — так будет видно, какой именно шаг
починил, и не накопятся лишние правки.

---

## Что нужно, чтобы починить точечно, а не перебором

Достаточно любого из:

* содержимое `/bitrix/urlrewrite.php` и `/catalog/index.php`;
* точный URL сломанного раздела (например
  `https://sport-trend.ru/catalog/legkaya-atletika/`) и что именно на нём
  открывается;
* доступ по SSH/FTP или в админку.

По этим данным причина определяется однозначно и правится одним изменением.
